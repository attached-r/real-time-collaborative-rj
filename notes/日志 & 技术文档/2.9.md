因为大二阶段对计算机网络还不熟悉，我用**最像聊天、最接地气**的方式，从零开始把整个流程讲清楚，就像在教朋友一样。

### 1. 先搞懂：为什么需要 WebSocket？（和 HTTP 到底有啥区别）

平时你打开网页是这样的：

- 浏览器：服务器大哥，我要看这个页面！（发 HTTP GET 请求）
- 服务器：好，给你内容！（发 HTTP 响应）
- 然后连接就断了。下次要刷新、再发请求、再握手（短连接）

这适合“看网页、点链接”，但不适合“实时聊天、在线协作、股票价格跳动”这种场景——因为服务器想随时推消息给浏览器时，浏览器根本没在“等着”。

**WebSocket 就是把这条路改成“双向一直开着的视频会议”**：

1. 第一次还是用 HTTP 发起（带特殊 header：Upgrade: websocket）
2. 服务器同意后，连接升级成 WebSocket（TCP 长连接）
3. 从此双方都能随时说话，不用每次都问“在吗”“在”“我说话了”“收到”

**大白话比喻**：
- HTTP = 发微信语音，一条一条发，发完结束
- WebSocket = 直接开语音通话，麦克风一直开着，谁想说话就说

### 2. 光有 WebSocket 还不够，为什么要加 STOMP？

高速公路修好了，但如果大家乱发消息（“今天天气不错”“你吃饭了吗”“文档改了”），别人根本不知道这条消息是发给谁的、是干嘛的。

**STOMP 就是这条高速公路上的“交通规则 + 广播喇叭系统”**。

它定义了几个常用指令（像微信群里的命令）：

- **CONNECT**：我要进聊天室了（连接 + 带身份证明）
- **CONNECTED**：欢迎加入！（服务器同意）
- **SUBSCRIBE**：我想听“文档123更新”这个频道（订阅主题）
- **SEND**：我往服务器发消息（比如“文档改了”）
- **MESSAGE**：服务器广播给所有人（“文档改了，大家看”）

**生活比喻**：
- 你进群聊 → CONNECT（刷门禁卡）
- 群主同意 → CONNECTed
- 你说“我要听群公告” → SUBSCRIBE /topic/announcement
- 你发消息“大家晚上聚餐” → SEND /app/chat
- 服务器广播 → 所有订阅了 /topic/chat 的人都收到

Spring Boot 把 STOMP 集成得很完美：你写几行配置，它就自动帮你处理这些“指令”。

### 3. Spring Boot 底层是怎么干活的？（分层流程图）

```
浏览器               Spring Boot 后端
   │                     │
   │  HTTP Upgrade       │
   │─────────────────────►│  ← WebSocketHandler 接管
   │  ws://localhost:8080/ws  │  升级 HTTP → WebSocket 长连接
   │                     │
   │  STOMP CONNECT + Authorization: Bearer xxx  │
   │─────────────────────►│  ← ChannelInboundChannel
   │                     │    ← JwtChannelInterceptor 拦截
   │                     │      → 验证 token
   │                     │      → 设置 SecurityContext（记住你是谁）
   │  CONNECTED         │
   │◄────────────────────│
   │                     │
   │  SUBSCRIBE /topic/document/123  │
   │─────────────────────►│  ← MessageBroker 记录订阅
   │                     │
   │  SEND /app/document.update  │
   │─────────────────────►│  ← 路由到 @MessageMapping 方法
   │                     │    → 业务逻辑（保存内容）
   │                     │    → SimpMessagingTemplate.convertAndSend("/topic/document/123", 新内容)
   │  MESSAGE           │
   │◄────────────────────│  ← 推给所有订阅者（实时更新）
```

**一句话总结底层流程**：

> 浏览器先用 HTTP 握手 → Spring 把连接升级成 WebSocket → STOMP 协议接管这条通道 → CONNECT 时用拦截器验证 JWT → 后续消息自动带用户身份 → 服务器用 MessageBroker 负责广播和路由

### 4. 为什么认证要放在 CONNECT 阶段？

因为 WebSocket 连接一旦建立，就不会再走普通的 HTTP Filter Chain（不像 REST API 每次请求都有 SecurityFilter）。

所以 Spring 专门提供了 `ChannelInterceptor`，让你在 STOMP 消息层面拦截。

- 只拦截 CONNECT（连接时验证一次）
- 验证通过 → 把用户名放进 SecurityContext
- 后续所有 STOMP 消息（SEND、SUBSCRIBE）都能复用这个上下文

**比喻**：就像进 KTV 包厢，先刷会员卡（CONNECT），刷完后整个晚上唱歌都不用再刷（后续消息自动知道你是谁）。
