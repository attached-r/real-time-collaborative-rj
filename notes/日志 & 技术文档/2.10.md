### 关键技术：WebSocket + STOMP 机制详解（通俗版）

**WebSocket 是什么？**  
平时我们用 HTTP 是“一问一答”：浏览器问“给我这个文档”，服务器回“给你”，然后连接就断了。  
**WebSocket** 就像把这条路改成**一直开着的视频会议**：连接一旦建立，双方可以随时说话，不用每次都重新握手。

**为什么还要加 STOMP？**  
光有高速公路不够，还需要**交通规则**。  
STOMP 就是规则，它定义了：
- **CONNECT**：我要进会议室（带 token 认证）
- **SUBSCRIBE /topic/xxx**：我要听这个房间的广播
- **SEND /app/edit/xxx**：我向服务器发消息（我编辑了）
- **MESSAGE**：服务器推消息给所有人（别人编辑了）

**前后端联调完整流程（第9天实现）**：

```
浏览器（前端）                          后端（Spring Boot）
     │                                      │
     │  HTTP Upgrade → ws://localhost:8080/ws   │
     │─────────────────────────────────────►│
     │  CONNECT + Authorization: Bearer xxx    │
     │─────────────────────────────────────►│ ← JwtChannelInterceptor 验证 token
     │  CONNECTED                              │
     │◄─────────────────────────────────────│
     │                                         │
     │  SUBSCRIBE /topic/{docId}               │ ← 订阅房间
     │─────────────────────────────────────►│
     │  SEND /app/edit/{docId} + 内容          │ ← 用户编辑时发送
     │─────────────────────────────────────►│ ← @MessageMapping 收到
     │                                         │   → applyDelta 处理
     │  MESSAGE /topic/{docId} + 新内容        │ ← @SendTo 广播
     │◄─────────────────────────────────────│
```

**当天核心代码对应**：
- 前端发送 → `/app/edit/{docId}`
- 后端接收 → `@MessageMapping("/edit/{docId}")`
- 后端广播 → `@SendTo("/topic/{docId}")`

### 前后端联调详细流程（重点讲解）

**1. 连接阶段（CONNECT）**
- 前端：`new Client({ connectHeaders: { Authorization: `Bearer ${token}` } })`
- 后端：`JwtChannelInterceptor` 拦截 CONNECT 帧 → 验证 token → 把用户名存到 `sessionAttributes`
- 成功后返回 `CONNECTED`

**2. 订阅阶段（SUBSCRIBE）**
- 前端：`client.subscribe(`/topic/${docId}`, callback)`
- 后端：记录该客户端订阅了这个主题（MessageBroker 管理）

**3. 发送编辑阶段（SEND）**
- 前端：用户输入时 `client.publish({ destination: `/app/edit/${docId}`, body: JSON.stringify(content) })`
- 后端：`@MessageMapping("/edit/{docId}")` 收到 → 调用 `applyDelta` → 处理后通过 `@SendTo` 广播

**4. 广播接收阶段（MESSAGE）**
- 后端：`@SendTo("/topic/{docId}")` 把结果推给所有订阅者
- 前端：订阅回调收到 `message.body` → `doc.value.content = receivedContent`

**当前问题根源（为什么同步不稳定）**：
- 前端每次输入都发送**完整内容**
- 后端每次都**追加**到现有内容
- 广播回去后前端又覆盖 → watch 再次触发 → 无限循环追加 → 内容爆炸

## 前后端联调机制深度解释（大二友好版）

**比喻**：  
想象一个**多人实时会议室**：

- **WebSocket** = 会议室的视频通话一直开着（长连接）
- **STOMP** = 会议室的规则（谁发言、谁听哪个频道）
- **/app/edit/{id}** = “我发言了”（发给服务器处理）
- **/topic/{id}** = “群公告频道”（服务器广播给所有人）
- **JwtChannelInterceptor** = 进门刷卡（CONNECT 时验证身份）
- **sessionAttributes** = 给这个人贴上名字标签（后续消息都知道是谁）

**完整一次编辑流程**：
1. 用户A 输入文字 → 前端发送增量到 `/app/edit/123`
2. 后端 `handleEdit` 收到 → 调用 `applyDelta` 处理（追加、保存）
3. 后端通过 `@SendTo("/topic/123")` 广播完整新内容
4. 用户B（订阅了 `/topic/123`）收到 MESSAGE → 更新自己的编辑器
